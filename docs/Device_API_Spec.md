## 1. What changed from the proposal (quick summary)

| Proposal [P] | Now [S] | What it means for firmware |
|---|---|---|
| Scan = daily attendance | Scan belongs to a **class session** | Firmware does **not** need to know schedules. Send UID + time; the server decides which class |
| One device | **One device per room**, shared by many classes | Firmware is the same for every room; only `device_id` and `device_key` differ |
| Upload record to Google Sheets | Upload to an Apps Script API with **device authentication** | Every request includes `device_id` + `device_key` |
| Offline buffer, remove after confirmation | Same, plus a **unique `scan_id`** per scan | Prevents duplicate rows when a retry happens |
| Feedback: accepted / duplicate / unregistered | Same three, plus new results (not enrolled, no class now, saved offline) | Mostly new **LCD text**; LED/buzzer mapping to agree on (Section 8) |

Hardware is unchanged. No new components are required by this spec.

## 2. Division of work

| ESP32 does | Server does |
|---|---|
| Read UID, normalize it | Verify device key |
| NTP time sync, timestamp each tap | Find the room of the device |
| Local double-tap cooldown (default 5 min) [P] | Find the class session from schedule + time |
| Generate `scan_id` | Check card is active, student is enrolled |
| Upload, or queue in LittleFS if it fails [P] | Prevent duplicates (per `scan_id` and per session) |
| Show LED/buzzer/LCD result [P] | Decide PRESENT vs LATE |
| Report battery, Wi-Fi, queue size [P] | Store attendance and logs; return a result per scan |

## 3. Transport

| Item | Value |
|---|---|
| URL | One Apps Script Web App URL ending in `/exec` (provided later). Keep it in the secrets config, not in GitHub |
| Method | `POST` |
| Protocol | HTTPS (`WiFiClientSecure` + `HTTPClient`) |
| Header | `Content-Type: application/json` |
| Body | JSON with an `action` field (Section 6) |
| Timeout | ~15 s per request [R]. Apps Script can be slow on the first call after idle |
| HTTP status | Apps Script replies **200** even for errors. **Always read the JSON `ok` field.** Never treat "HTTP 200" alone as success |

### 3.1 Redirect handling (important)

Apps Script processes the POST, then answers **HTTP 302** with a `Location` header. The actual JSON result is at that Location and must be fetched with **GET**.

Known pitfalls:
- `HTTPC_FORCE_FOLLOW_REDIRECTS` re-sends the **POST** with the same body to the new URL. The redirect host has no POST handler, so this fails (reported as HTTP 405).
- Reusing one `WiFiClientSecure` across the host change (`script.google.com` → `script.googleusercontent.com`) can break the TLS session on ESP32.

Recommended procedure [R]:
1. `http.setFollowRedirects(HTTPC_DISABLE_FOLLOW_REDIRECTS)` and `http.collectHeaders(...)` for `Location`.
2. `POST` the body.
3. If the code is **302**: read `Location`, call `http.end()`, then make a **new** client and send a plain **GET** to that URL. Its body is the JSON response.
4. If the code is **200**: the body is already the JSON response.
5. Anything else, a failed GET, or a body that is not valid JSON → **treat as failed** and keep the scan in the queue.

Why it's safe to retry: the POST may already have been saved even if step 3 fails. When the device retries, the server recognizes the same `scan_id` and returns `ALREADY_RECORDED` instead of creating a second row.

### 3.2 TLS certificate [?]
Validating Google's root CA is preferred over `setInsecure()`. If root-CA validation causes problems on your board, tell the software side so we document the trade-off.

## 4. Device authentication [R]

Every request includes:

| Field | Type | Example | Notes |
|---|---|---|---|
| `device_id` | string | `DEV-RM301-01` | Assigned by admin; one per room |
| `device_key` | string | 32+ random characters | Generated by admin, shown once. Server stores only a hash |

Rules:
- Store both in a secrets file that is in `.gitignore`. **Never commit them.**
- If the server answers `INVALID_DEVICE_KEY` or `DEVICE_DISABLED`, **keep all queued scans** and show "Device error". The admin may have rotated the key.
- Students' and instructors' Google logins are **never** used on the device.

(Possible later upgrade: HMAC request signing instead of sending the key. Not required for the MVP.)

## 5. Time, UIDs, and scan IDs

### 5.1 Time [P + R]
- Sync with NTP at boot and periodically (e.g., every 1–6 hours) [P].
- Send all times as **Unix epoch seconds (UTC)**. The server converts to Asia/Manila.
- Every server response includes `server_time` (ISO 8601). If the device clock differs by more than ~2 minutes, re-sync NTP [R].

`time_quality` values:

| Value | When |
|---|---|
| `ntp` | Clock was synced when the card was tapped |
| `backfilled` | Tap happened **before** NTP sync in the same power cycle; time was calculated after sync as `now − (millis_now − millis_at_scan)` |
| `unverified` | No NTP sync ever happened before power was lost. Send `scanned_at: 0`. The server will log it as `INVALID_TIME` for manual review |

No RTC module is in the component list, so `unverified` is a known limitation [?].

### 5.2 UID format
Uppercase hexadecimal, **no spaces or colons**, all UID bytes in reader order.
Example: bytes `04 A1 B2 C3` → `"04A1B2C3"`. (7-byte UIDs → 14 hex characters.)

### 5.3 `scan_id` (unique per tap) [R]

```
scan_id = <device_id>-<boot_count:6 digits>-<sequence:6 digits>
example:  DEV-RM301-01-000042-000317
```

- `boot_count`: stored in NVS (`Preferences`, part of the ESP32 core), **incremented at every boot**.
- `sequence`: counter in RAM, starts at 1 each boot, increments per accepted tap.
- Created **at tap time** and **never changed**, including when the scan is retried from the queue.
- Do **not** create a `scan_id` for taps blocked by the local cooldown (they are not sent).

## 6. Actions

### 6.1 `device.submitScans` — send 1 to 20 scans

Used for both live scans (1 item) and queue sync (batch). One code path.

**Request**
```json
{
  "action": "device.submitScans",
  "device_id": "DEV-RM301-01",
  "device_key": "<secret>",
  "sent_at": 1793750712,
  "firmware_version": "0.3.0",
  "scans": [
    {
      "scan_id": "DEV-RM301-01-000042-000317",
      "rfid_uid": "04A1B2C3",
      "scanned_at": 1793750710,
      "time_quality": "ntp",
      "sync_mode": "live"
    }
  ]
}
```

| Field | Required | Notes |
|---|---|---|
| `sent_at` | Yes | Current device time (epoch), or 0 if not synced |
| `scans[]` | Yes | 1–20 items, oldest first |
| `scans[].sync_mode` | Yes | `live` = sent right after the tap; `offline` = sent from the queue |

**Response**
```json
{
  "ok": true,
  "server_time": "2026-11-04T08:05:13+08:00",
  "data": {
    "results": [
      {
        "scan_id": "DEV-RM301-01-000042-000317",
        "result": "ACCEPTED",
        "attendance_status": "PRESENT",
        "final": true,
        "lcd_line2": "J. Dela Cruz"
      }
    ],
    "roster_version": 12
  }
}
```

- One result **per scan_id**, same order as the request.
- `lcd_line2` is at most 16 characters (server truncates). It may be empty.
- `roster_version`: if it is newer than the device's, call `device.getRoster`.

### 6.2 `device.heartbeat` — status report (every 5 minutes [R])

**Request**
```json
{
  "action": "device.heartbeat",
  "device_id": "DEV-RM301-01",
  "device_key": "<secret>",
  "sent_at": 1793750712,
  "battery_voltage": 3.82,
  "wifi_rssi": -61,
  "queue_count": 0,
  "time_synced": true,
  "firmware_version": "0.3.0",
  "uptime_seconds": 5400
}
```

`battery_voltage` = the **actual** battery voltage after the voltage-divider conversion [P], in volts, 2 decimals.

**Response**
```json
{
  "ok": true,
  "server_time": "2026-11-04T08:05:13+08:00",
  "data": { "roster_version": 12, "low_battery": false }
}
```

The low-battery alert itself is shown on the **dashboard** [P]. `low_battery` is returned so the LCD can also show a warning if the team wants it [?].

### 6.3 `device.getRoster` — cached student list and settings

The proposal requires the student list to be cached in flash [P]. It is used **only when offline** (Section 7).

**Request**
```json
{
  "action": "device.getRoster",
  "device_id": "DEV-RM301-01",
  "device_key": "<secret>",
  "known_version": 11
}
```

**Response (changed)**
```json
{
  "ok": true,
  "server_time": "2026-11-04T08:05:13+08:00",
  "data": {
    "changed": true,
    "roster_version": 12,
    "settings": { "duplicate_window_minutes": 5, "heartbeat_interval_seconds": 300 },
    "cards": [
      { "uid": "04A1B2C3", "name": "J. Dela Cruz" },
      { "uid": "04D5E6F7", "name": "M. Santos" }
    ]
  }
}
```

**Response (not changed):** `{ "ok": true, "data": { "changed": false, "roster_version": 11 } }`

- Contains **active cards only** (revoked cards are excluded).
- Save to LittleFS (e.g., `/roster.json`); replace the old file only after the new one is fully written.
- Call at boot, whenever `roster_version` in a response is newer, and at least every few hours.

### 6.4 Request-level errors (`ok: false`)

```json
{ "ok": false, "server_time": "...", "error": { "code": "INVALID_DEVICE_KEY", "message": "..." } }
```

| Code | Device action |
|---|---|
| `INVALID_DEVICE_KEY`, `DEVICE_DISABLED` | Keep queue; LCD "Device error"; retry slowly (every 5 min) |
| `DEVICE_NOT_ASSIGNED` | Same as above (admin must assign a room) |
| `BAD_REQUEST` | Firmware bug — keep queue, log to Serial |
| `SERVER_BUSY`, `SERVER_ERROR` | Keep queue, retry with backoff |

## 7. Scan flow on the device

```
Tap card
  │
  ├─ Same UID tapped within duplicate_window? ──Yes──► "Already scanned" feedback (not sent, not queued) [P]
  │
  ├─ Create scan_id + timestamp
  │
  ├─ Wi-Fi connected?
  │     ├─ Yes ─► LCD "Processing..." ─► submitScans (sync_mode: live)
  │     │           ├─ final result ─► show feedback for that result (Section 8)
  │     │           └─ failed / timeout / not JSON ─► append to queue ─► "Saved offline"
  │     │
  │     └─ No ──► UID in cached roster?
  │                 ├─ No  ─► "Unregistered" feedback (not queued) [P]
  │                 └─ Yes ─► append to queue (sync_mode: offline) ─► "Saved offline"
```

Notes:
- **Online, unknown UID is still sent to the server** [R]. The cached roster may be outdated (e.g., a card registered 5 minutes ago), and the server logs unknown UIDs so the admin can register new cards by tapping them.
- The **local cooldown** only records the tap time after an `ACCEPTED`, `DUPLICATE`, or "Saved offline" outcome, not after rejections, so a student who got "No class now" can tap again later [R].

### 7.1 Offline queue rules [P + R]

| Rule | Detail |
|---|---|
| Storage | LittleFS file, one JSON object per line (e.g., `/queue.jsonl`) [P] |
| Write first | If a live upload fails, the scan is appended **before** showing "Saved offline" |
| Upload order | Oldest first, batches of up to 20 |
| Removal | Remove a scan **only** when its result has `"final": true` [P] |
| Retry | Backoff: 10 s → 30 s → 60 s → 5 min (max) while Wi-Fi is up; retry immediately on Wi-Fi reconnect |
| New taps while syncing | Keep accepting taps; live taps may be sent immediately or queued behind — firmware's choice [?] |
| Capacity | Set a maximum (e.g., 500 scans) [?]. At ~90% show "Storage almost full". When full: **refuse new taps** with "Storage full" — never delete or overwrite old scans [R] |
| Feedback during sync | Results received while draining the queue are **not** shown on the LCD (the student already left). The server keeps them in its logs |
| Reporting | Send `queue_count` in every heartbeat |

## 8. Scan results and feedback

### 8.1 Result codes

| `result` | Meaning | `final` |
|---|---|---|
| `ACCEPTED` | Saved. `attendance_status` is `PRESENT` or `LATE` | true |
| `ALREADY_RECORDED` | Same `scan_id` was already processed (retry). Contains the original result | true |
| `DUPLICATE` | Student already has attendance in this session | true |
| `UNREGISTERED` | UID not linked to an active card | true |
| `NOT_ENROLLED` | Valid student, but not enrolled in the current class | true |
| `NO_ACTIVE_SESSION` | No class in this room at that time | true |
| `SESSION_CANCELLED` | The class session was cancelled | true |
| `INVALID_TIME` | Timestamp unusable (`unverified`, or far outside reasonable range) | true |
| `RETRY_LATER` | Server could not process this scan right now | **false** — keep it |

All `final: true` results are stored on the server, so removing them from the queue never loses information.

### 8.2 Feedback table (to agree with the hardware team)

LCD is 16×2, so every line is 16 characters or fewer.

| Situation | LED | Buzzer | LCD line 1 | LCD line 2 | Tag |
|---|---|---|---|---|---|
| `ACCEPTED` + `PRESENT` | Green | 1 short | `Recorded` | name (`lcd_line2`) | [P] |
| `ACCEPTED` + `LATE` | Green | 1 short | `Recorded - Late` | name | [R] |
| `DUPLICATE` (server) | — | 2 short | `Already recorded` | name | [P] |
| Local cooldown | — | 2 short | `Already scanned` | `Please wait` | [P] |
| `UNREGISTERED` | Red | 1 long | `Unregistered` | `Card not found` | [P] |
| `NOT_ENROLLED` | Red | 1 long | `Not enrolled` | `in this class` | [R] |
| `NO_ACTIVE_SESSION` | Red | 1 long | `No class now` | `Scan not counted` | [R] |
| `SESSION_CANCELLED` | Red | 1 long | `Class cancelled` | `Scan not counted` | [R] |
| Saved offline | Green [?] | 1 short [?] | `Saved offline` | `Will sync later` | [?] |
| Waiting for server | — | — | `Processing...` | — | [R] |
| Device/auth error | Red | 3 short | `Device error` | `Contact admin` | [R] |
| Queue full | Red | 1 long | `Storage full` | `Tell instructor` | [R] |
| Idle | — | — | `Tap your ID` | room or Wi-Fi status | [R] |

Design rule for the new results: they reuse the proposal's **red + long beep** "rejected" pattern and differ only in LCD text, so no new hardware is needed [R].

Open question [?]: Should "Saved offline" use the same green + short beep as "Recorded"? The proposal flowchart shows green only after a confirmed upload. A saved-offline scan is safely stored but not yet confirmed, and the server may later reject it (e.g., not enrolled). Alternatives: green LED blink twice, or green with no beep.

## 9. Testing checklist for firmware

Before the real server exists, test parsing with the JSON examples above. After the server is deployed:

1. Registered card → `ACCEPTED`, green + short beep, correct name.
2. Same card again within 5 min → local "Already scanned", nothing sent.
3. Same card after 5 min, same class → server `DUPLICATE`.
4. Unknown card while online → server `UNREGISTERED`, appears in admin's unregistered list.
5. Unknown card while offline → local "Unregistered", not queued.
6. Wi-Fi off, tap 5 registered cards → 5 lines in queue, "Saved offline".
7. Wi-Fi on → queue drains, 5 records on the server, **no duplicates**.
8. Cut the connection **after** POST but before GET (simulate by stopping after step 2 of 3.1) → retry gives `ALREADY_RECORDED`, still one record.
9. Reboot with a non-empty queue → queue survives and syncs; `boot_count` increased, no `scan_id` collision.
10. Boot with no Wi-Fi, tap, then connect → `time_quality: backfilled` with a correct time.
11. Wrong `device_key` → "Device error", queue kept.
12. Heartbeat → dashboard shows battery voltage matching a multimeter reading [P].
13. Measure tap-to-feedback delay (live) [P: Cloud Synchronization Delay test].
